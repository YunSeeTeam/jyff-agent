## 3. 各阶段要点

### 3.1 阶段 0：准备与决策

三项可并行，均不修改业务代码。

- **开发前确认（原方案 12.3）。** 核对本地分支与基线的差异；确认锁定的 Pi 0.82.1 具备方案依赖的 custom entry、`getEntry` 与原始 parent 链 API；确认 Docker 运行平台与资源能力。项目支持 Windows→WSL 路径，而 attached pipes 在该路径下的可行性是设计说明书第 17 章的未决项，需在此记录实际平台。
- **U0 Pi 版本选型。** 记录候选版本、依赖图、API/存储差异、负责人与复审里程碑。U0 须在 P1-b、P2、P3 的 Pi 耦合设计冻结前完成；P0 不等待它。2026-11-03 维护者决定升级到官方最新版本（R2），在阶段 1.5 实施；此前保持精确锁定 0.82.1。
- **P0-a 评测基线。**
  - 每个样本使用独立数据根（RunStore、黑板、原生 Session、workspace、平台已解状态）。
  - 由评测器在外部强制整题墙钟；各阶段始终由独立评测器保持同等测试时间；该限制不进入产品。
  - 平台 accepted 以只读方式观测（A-observed），不改变 prompt、派发或停止行为。
  - 先跑 A-original，失败、限流与故障样本全部保留。

### 3.2 阶段 1：正确性修复

三项互不依赖，可分别发布。P0-d 是 A-original 评测中新发现的缺陷，补入本阶段。

- **P0-d 网络瞬断分类。** OpenAI/Anthropic SDK 的 `Connection error.` 等连接失败只以文本到达分类器，被判为不可重试并计入阻塞，数秒内连续几次就把题目判为 blocked。改为按网络瞬断带退避重试，并沿错误的 `cause` 链读取错误码。
- **P0-b accepted 成功事实。**
  - `runs` 新增 `solve_outcome`、`observed_accepted_at`、`platform_accepted_at`、`writeup_status`。
  - 提交工具在成功事实提交数据库后才返回 accepted。
  - writeup 失败不再清除 accepted；cleanup 错误独立记录。
  - 崩溃恢复覆盖 `blocking`、`writing_writeup`。
  - 建立 `runtime_data_capabilities` 登记，后续每次加列沿用这套幂等迁移方式。
- **P0-c 子模型压缩修复。**
  - CtfSubagent 使用专用 `SUBAGENT_COMPACTION_PROMPT`。
  - 恢复工具集 = 旧 activeToolNames ∩ 角色合法集合 ∩ 当前阶段合法集合。
  - writeup 阶段仍只有 read/write/edit/list。
- **前置理由。** 不修 P0-b，writeup 失败会改写运行状态，后续所有对照组的成功口径都不可信。

### 3.3 阶段 1.5：Pi 运行时迁移

目标版本为开始实施时官方的最新稳定版（2026-11-03 为 1.5.0），`pi-agent-core`、`pi-ai`、`pi-coding-agent` 同版本并精确锁定。`pi-durable` 是独立的文档/任务运行时，职责与 RunStore 和调度器重叠，不纳入本次迁移。

**为什么放在这里。**

- A-fixed 先在旧运行时上测完，升级后用同一配置再测一次（A-fixed-pi），可以把运行时本身的影响与工作流改动分开（设计说明书 U10）。
- 阶段 2 的 runtimeProfile、阶段 3 的 P1-b 执行边界与 P2 技能加载、阶段 4 的逐请求取消/恢复接线都直接依赖 Pi 接口。先迁移再做，可避免在旧 API 上做一遍、迁移时再重写一遍。
- 阶段 1 的修复全部在 jyff 自身代码中，不依赖 Pi 版本，迁移时按回归用例验证即可。

**内容。**

1. **U1 隔离原型**（独立分支/worktree）：1.x 已从 core 移除 `AgentHarness`、`Session`、`JsonlSessionStorage`、`ExecutionEnv`、内置工具、技能与压缩等 31 个本项目使用的符号及 `./node` 子路径（按官方 tarball 的类型声明与本仓库实际导入逐项比对得出）。按设计说明书 18.4 节建立 `AgentRuntimeAdapter`、`ExecutionTranscriptReader`、`ModelRequestPolicy`、`ConversationReader/Exporter` 四个窄接口，改接 BaseAgent/Session、DockerExecutionEnv、工具、技能、压缩、模型注册与 HTML 导出。
2. **U2 兼容验收**：U01—U10 中适用的检查；阶段 0/1 的全部用例回归；旧 JSONL 会话至少可只读浏览；Pi 契约测试（`pi-session-contract.test.ts`）按新存储合同改写并通过。
3. **U3 冻结**：精确版本与完整锁文件；记录 runtimeProfile；先在新 Run 上小批放量。

**实施结果。**

- BaseAgent 改为基于 pi-coding-agent 的 `AgentSession` 与 `SessionManager`，公开接口基本不变；Core 与后端改用 jyff 自有的 `BaseAgentEvent`。
- 容器内 read/write/edit/bash 由 jyff 维护：1.x 的同名工具按宿主机规则解析路径，Windows 宿主会把 `/workspace/x` 解析成盘符路径；bash 还会把截断输出写进宿主机临时文件。移植的工具保持 0.82 的模型可见行为。
- Pi 的自动 compaction 与自动重试关闭，由 Core 负责；小上下文窗口下保留的近期上下文上限为可用窗口的一半，避免 1.5 拒绝压缩。
- 工具集记录为 `jyff.active_tools` 自定义条目；0.82 会话（`active_tools_change` 等旧条目）可继续打开和恢复。
- `pi-session-contract.test.ts` 已按 SessionManager 合同改写。
- 回退限制（U09）：0.82 的读取器能打开 1.5 写入的会话且不报错，但会把 system 消息当作普通上下文，并丢失工具集记录。回退到 0.82 前，不得续跑新运行时创建的 Run；阶段 2 的 Run 配置冻结记录 runtimeProfile 后，由它负责拦截。

**出口门。** 上述检查全部通过，`vp check / typecheck / test / build` 全绿，A-fixed-pi 与 A-fixed 同配置对照无明显回归（小样本只能发现明显回归）。迁移不与阶段 2 及之后的功能同时放量。

### 3.6 阶段 4：持续求解与故障恢复（工程实现完成）

按维护者 2026-11-15 决策撤销原预算阶段；不实现 budgetId、预算账本、费用预留、整题截止、收尾费用上限或产品限额模式。预算守护永久留在独立评测工具。内部顺序：

1. `retryRun()` 并入持久入队；冻结求解目标与暂停/恢复状态合同。单次尝试结束和固定重试次数不能自动放弃未解目标；保留证据、已试路径与人工停止意图（修订 T24、T28）。
2. 模型请求/流空闲超时、取消与可观测重试覆盖所有入口；瞬断计数按连续失败计数，有进展后清零。限流、网络或订阅配额暂不可用时保存进度并退避/暂停，恢复后继续（修订 T25—T27）。
3. accepted 后停止探索，独立处理 writeup/清理；补齐 `accepted_persistence_failed` 重启证据对账，不能将平台当前已解伪造成原 Run 的接受归属和原始时间。
4. 验证平台确认 accepted 或人工停止的产品终止语义；请求/命令超时只用于恢复或换路。真实测试仍由评测器在外部施加已授权的费用/墙钟限制，不作为产品入口。

2026-11-15 已按上述顺序实现：持久目标与 retry/writeup 入队、生产无限次续跑、连续失败退避、逐请求超时/取消/归属、接受回执恢复及页面恢复入口。T24—T28 免费本地回归包含实际 Pi 压缩/分支摘要/SubAgent 入口；完整检查 924 通过、11 跳过。未调用付费模型，不新增产品预算配置。新数据能力 `continuous-solve-goals: 1` 限制不兼容回退。阶段 3 的付费效果结论仍为受限 2/12；阶段 5/6 未开始。

发布前按设计复核并补修四项问题（提交 `54ac10d`）：准备失败后的 retry 提示词丢失、不可用重启期间移出空闲项后被重新加入、人工标记已解被提升为 accepted、更新清单缺少持续求解数据能力声明。四项均先以离线回归复现后修复；Solver 默认提示词也同步去掉自行放弃的旧措辞。924 个测试通过，未进行新增付费或外部题目评测。

### 3.7 阶段 5：本地进程与实验证据

- SQLite 唯一键原子保留 requestKey；会话与日志配额。
- 仅设单作业截止用于回收卡死资源；poll/write 不延长，不设整题累计截止。
- 原始日志按字节范围读取；实验记录与 artifactRef。
- 重启扫描所有 cleanup 未确认记录，不止 `markInterruptedRuns()` 的返回集合。
- PTY 不在本期。
- P4-a 样例（`DockerProcessSession`）在真 Docker（Windows→WSL）中验证了 attached pipes、原始字节双流、两轮 stdin、EOF 与停止，并暴露三项生产约束：
  - 宿主侧结束 `docker exec` 客户端不会停止容器内进程；停止只能在容器内向整个进程组发信号。
  - runc 下 `docker exec` 启动的进程已经是会话与进程组首进程。此时无条件调用 `setsid` 会 fork，attached 客户端看到的是父进程的退出码 0，而不是命令本身的结果。
  - P4-a 观察到 PID 1 为 `sleep infinity` 时，孤立子进程未被回收且继续占用 PID 额度。2026-11-18 已增加 `--init`，并在真实 Linux 容器中观察到孤立子进程由 PID 1 接管，退出后其 `/proc` 条目消失。

2026-11-18 部分交付。题目「文件」页可对大文件和二进制按原始字节分页。选定 Run 后，操作者可冻结完整文件或固定前缀、校验 SHA-256 并登记实验。重启时分别处理各 Run 未确认的容器清理；一个会话关闭失败仍会继续回收其余资源。旧数据升级后按 Project 和 Run 标签核查历史容器一次。

## 4. 关键路径与并行

```text
阶段0  U0 ∥ P0-a 评测器 ∥ 开发前确认
  ↓
阶段1  P0-d ∥ P0-b ∥ P0-c             → 评测 A-fixed
  ↓
阶段1.5 Pi 运行时迁移 U1→U2→U3        → 评测 A-fixed-pi
  ↓
阶段2  底座/接口冻结    ∥ P4-a 样例（只改 sandbox）
  ↓
阶段3  P1-a ∥ P1-b ∥ P2               → 评测 B → C
  ↓    （P3 可在 P1-b 第 2 步合入后启动）
阶段4  P3 持续求解与故障恢复
  ↓
阶段5  P4-b（需要 P3 与 P4-a）          → 评测 D
  ↓
阶段6  P5                             → 评测 E
```

关键路径为 阶段 1.5 → 阶段 2 → P1-b → P3 → P4-b → P5。阶段 1.5 与 P1-b、P3 工作量最大，且集中修改 `base-agent`、`session.ts`、`project.ts`、`subagent-manager.ts`、`contest-scheduler.ts`，人手有限时优先保证它们不排队。

阶段 1.5 只阻塞依赖 Pi 接口的部分；不依赖 Pi 的 P4-a 原型可以与它并行。迁移不与阶段 2 及之后的功能同时放量，以免故障归因与数据回退无法区分。
